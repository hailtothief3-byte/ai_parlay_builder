# AI Parlay Builder Sale Package

## Purpose

This document is a low-conversation sale package for AI Parlay Builder.

It is designed to help a buyer understand:

- what the product is
- why it is valuable
- what they would receive
- how transfer would work
- what questions to ask before buying

Use this as the main written handoff in a quiet sale process where the documents and demo do most of the selling.

## Asset summary

AI Parlay Builder is a workflow and intelligence platform for:

- prop research
- ticket construction
- DFS handoff packaging
- results review
- post-result learning

It is not positioned as an automated wager-placement tool.

## Why the asset is attractive

### 1. It is a working product, not just a codebase

The product already includes:

- a live hosted version
- a local run path
- guided workflow surfaces
- ticket memory
- review and grading workflows
- bankroll tracking
- DFS packaging support

### 2. It has an explainable intelligence layer

The product includes:

- smart pick scoring
- parlay leg audit
- review-driven recommendation loops
- backtest and CLV diagnostics in deeper modes

This makes it easier for an operator to trust, inspect, and tune.

### 3. It is easier to transfer than a typical side project

The repo already includes:

- setup guide
- config map
- deployment notes
- feature map
- buyer demo walkthrough
- buyer handoff summary
- buyer one-sheet
- plan matrix
- local buyer-demo checklist

That means a buyer does not need to reverse-engineer the product from scratch.

## Best buyer fit

This asset is most likely to fit:

- a solo operator
- a small sports workflow software studio
- a niche productivity-tool buyer
- a buyer who wants an existing product surface instead of a raw model library

## What the buyer receives

At minimum, a buyer-ready transfer should include:

- source code repository
- current documentation package
- business-kit documents
- local setup guidance
- deployment notes
- current product-plan packaging structure
- current live app URL and deploy context

## Recommended no-pressure sale process

If you want to sell this with as little marketing effort as possible, use:

### Step 1

Send the buyer:

- one-sheet
- short demo
- live app link
- asking-price range

### Step 2

Only if they stay interested, send:

- handoff summary
- plan matrix
- local demo checklist

### Step 3

Only if they are serious, do:

- short Q and A
- transfer discussion
- payment and repository transfer

This keeps the process document-led instead of conversation-led.

## Suggested buyer Q and A topics

If a serious buyer wants a short call, keep it focused on:

- current workflow coverage
- deployment path
- provider-key dependency
- live versus demo reliability
- transfer expectations

Avoid long open-ended strategy calls unless they are already close to buying.

## Current strengths

- production deployment already exists
- demo path works even when live-provider conditions are imperfect
- workflow is differentiated across `scan`, `build`, `track`, and `learn`
- product packaging is clearer than a typical internal-only Streamlit tool

## Current risks

- live workflows depend on provider keys and API availability
- Streamlit state should still be regression-tested after major changes
- some repo naming still reflects earlier starter-era history

## Strongest positioning line

Use this sentence when listing or describing the asset:

`AI Parlay Builder is a workflow and intelligence platform for prop research, ticket construction, DFS handoff, and post-result learning.`

## What should be prepared before listing the asset

Before seriously listing the product for sale, prepare:

1. one short recorded demo
2. 3 to 6 clean screenshots
3. an asking-price range
4. a transfer checklist
5. a note describing exactly what is included in the handoff
